# Curb Stamps — Handover, 2026-08-24

Everything below reflects real, verified repo/production state as of this
handover — not aspirational. Where something is untested or known-broken,
it's marked as such rather than assumed fine.

## What's actually done and live

**Printify catalog** — shop 28675131. Four product lines built across all 43
creatures (`dreg` was dropped — its recompose pipeline never worked cleanly,
not worth the fix):

| Category | Blueprint | Colours | Notes |
|---|---|---|---|
| Tee | 157 (Gildan 5000B) | 9: Black, White, Navy, Red, Royal, Orange, Purple, Irish Green, Light Pink | Sizes XS–XL |
| Hoodie | 314 (Gildan 18500B) | same 9 | Sizes S–XL (no XS on this blueprint) |
| Crewneck | 1256 (Gildan 18000B) | 5 only: Black, White, Navy, Red, Royal | This Gildan style genuinely doesn't come in Orange/Purple/Green/Pink — not a bug, checked the print provider's real colour list |
| Bucket hat | 6143 (ValuCap 2050, DTF print) | 5: Black, Navy, Red, Royal, White | Cap (embroidery) was dropped — the full lockup didn't survive embroidery scale/the cap's centre seam, owner's call to kill it rather than simplify the art |

Art position/scale was calibrated per-category against real Printify mockups
(not guessed): tee ≈15% from top, hoodie moved lower after visual review,
crewneck/bucket hat reused the tee baseline and checked clean on the widest
creature (Blob) and a tall one (Prick).

**Storefront (`curbstamps-site`)** — tee/hoodie/crewneck/bucket-hat product
pages and the shop grid pull *live* Printify data (real colours, sizes,
price, garment photos) via `src/lib/printify.ts` and the `withPrintifyData()`
overlay in `src/lib/products.ts`. Cap was removed from the site's `Category`
type entirely (no synthetic stand-in left for it).

Two real bugs found and fixed in that pipeline, worth knowing about if
similar symptoms show up again:
- Printify's `variant.options` array order (colour-id vs size-id) does **not**
  reliably follow the product's own declared options order — blueprint 314
  declares `[Colors, Sizes]` but its real variants carry `[sizeId, colourId]`
  anyway. Fixed by matching each id against which option-map it's actually a
  member of, not by position. Same bug, independently duplicated, existed in
  `curbstamps-admin`'s POD adapter — fixed there too.
- The in-process Printify catalog cache had no TTL (only checked truthiness,
  not age), so a long-running server would serve pre-change data forever.
  Fixed with a real 5-minute TTL.

**POD fulfilment (`curbstamps-admin`)** — `src/lib/pod/printify-adapter.ts`
is a real, tested implementation (verified against the live API: created a
test order, checked status, cancelled it — no charge, nothing sent to
production). `POD_PROVIDER=printify` **is set in production** right now.
`createOrder()` deliberately never calls Printify's `send_to_production`
endpoint, so nothing actually gets billed/printed even once a real order
flows through — that's a second deliberate gate, not just the missing
Stripe wiring below.

The inbound POD webhook (`/api/pod/webhook`) was rewritten against a real
captured payload (Printify's own `/webhooks/{id}/simulate`), not guessed —
verifies via HMAC-SHA256 (`x-pfy-signature`), 4 topics registered on the real
shop (`order:updated`, `order:sent-to-production`, `order:shipment:created`,
`order:shipment:delivered`).

**Creature line weight** — bumped from the original 4px to 7px (5px read as
no visible change). Live on: SVG masters, SVG lockups, the three downstream
PNGs per creature (icon/logo/logo-dark), and Printify product artwork/mockups
(confirmed on a real mockup image, not just an API 200). `CurbWorld.tsx`'s
separate background-scene creatures (`public/curbstamps/world/creatures/`,
stroke-width 18–30, a different asset system entirely, built by a different
session for an unrelated homepage feature) were deliberately left untouched.

Also cleaned up while in there: the deploy workflow used to run a hardcoded
CI step that replaced literal `stroke-width="4"` with `"5"` and
auto-committed the result on every deploy — harmless right now but a real
landmine for a future creature authored at the old 4px default. Removed, plus
fixed a stale smoke-test that was still asserting `"5"`. Also closed a gap
where Curb-only commits touching `docs/curbstamps/**` or
`deploy-curbstamps.yml` itself were triggering the *full* Shirtfaced stack
deploy alongside the Curb one — `deploy.yml`'s `paths-ignore` now covers both.

## What's outstanding / known broken

**Homepage lifestyle photos — the real open problem.** 13 composited photos
(creature print placed onto a real photo of a kid in a blank garment) are
wired into homepage rotation (`src/lib/homepage-photos.ts` +
`NewDropStrip`/`AdventureGrid`/`ShopByCategory`). Two separate issues:

1. **Print quality is genuinely not good enough.** The compositing is a flat
   alpha-overlay — no perspective warp, no shadow/lighting matching against
   the garment's own folds and light. It reads as a sticker pasted onto the
   photo rather than a real print. This is a property of the method, not a
   position/size tuning issue — expect it on all 13 photos, not just the
   ones actually inspected closely. Fixing this needs either a materially
   better compositing pass (multiply-blend for shadow pass-through + a slight
   perspective skew) or abandoning composited lifestyle photos in favour of
   something else (plain SVG stand-in, or real photography later).
2. **Bug, separately:** `AdventureGrid.tsx`'s bottom row (the small creature
   icon under each PLAY/EXPLORE/MAKE/BE word) still uses a *fixed* creature
   per slot (`CREATURES[1]/[3]/[6]/[9]`) that has nothing to do with which
   creature the randomly-rotated photo above it actually shows — e.g. the
   photo shows "Claw" but the icon below is a different creature entirely.
   `HomepagePhoto` needs a `creature` field so the icon can be picked to
   match whatever photo landed in that slot. Not fixed yet.

**Cap category** — fully dropped, not paused. If it comes back, it needs a
real design decision (icon-only mark, no wordmark, embroidery-appropriate
scale) before rebuilding, not just retrying the same lockup art.

**Crewneck colours** — only 5 of the usual 9. If that's not acceptable,
the only lever is a different blueprint/manufacturer (checked: Bella+Canvas
and the Rabbit Skins toddler crewneck both had worse coverage, not better).

**Payment is intentionally not wired.** Stripe keys are unset by design —
`checkout/PaymentStep.tsx` shows the honest "payment isn't connected" state.
This means the entire `markOrderPaid` → POD-adapter → Printify path has
**never fired from a real checkout**, only from my direct standalone test of
the adapter. Turning Stripe on is the thing that will actually exercise this
for the first time end-to-end.

**Order-item→Printify-slug plumbing** was fixed (`markOrderPaid` used to
send the POD provider a product's display name instead of its real slug) but
only unit-verified via the standalone adapter test, not via an actual
Stripe-paid order, since there isn't one yet.

## Where things live

- Printify build/update scripts (ad hoc, not in the repo): were run directly
  against the API this session, not committed anywhere. If the catalog needs
  rebuilding, that logic isn't sitting in a script waiting to be re-run.
- `curbstamps-site/scripts/refresh-printify-art.mjs` — the *only* Printify
  script that's actually in the repo and deploy-wired; re-uploads current
  lockup art to matching products on every Curb deploy.
- `assets/curbstamps/mockup-photos/` — the raw AI-generated blank-garment
  source photos and crops used for the 13 homepage composites (local only,
  not synced anywhere else).
- `curbstamps-site/public/curbstamps/homepage/` — the 13 deployed composite
  PNGs.
