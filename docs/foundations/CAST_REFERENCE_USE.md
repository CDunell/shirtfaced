# Cast references — storage and use

**Status:** ACTIVE production asset. Companion to `CHARACTERS.md`, `CAST_REFERENCE_PROMPTS.md` and `CHARACTER_CONTINUITY.md`.  
**Date:** 15 August 2026.  
**Reviewed:** 16 August 2026.

---

## 1. What a reference is for

`CHARACTER_CONTINUITY.md` §10 establishes the governing principle: **a recurring campaign character cannot exist only as a prompt paragraph.**

The approved image reference is the visual continuity mechanism. It carries the actual face/body appearance more reliably than repeatedly redescribing the person in prose.

After references, provider-facing scene prose should spend most of its detail budget on the **moment, place, light, camera, blocking and action**. Character identity is resolved by the production manifest and supplied reference assets.

A reference prompt is not the character. A seed is not the character. **The approved reference file/version is the visual asset.**

---

## 2. Authority relationship

Production identity is split deliberately:

1. `CHARACTERS.md` — narrative canon: who the person is, relationships and owner-set facts.
2. This document + approved `studio/var/cast/<slug>/` files — canonical visual identity/version.
3. `CHARACTER_CONTINUITY.md` — current scene appearance/wardrobe state.
4. Shot/scene contract — blocking, action and camera for the specific image/video.

The generator is below all four.

If an approved reference shows no tattoo, a scene prompt that merely omits the word `tattoo` does not grant permission to invent one. The same applies to scars, piercings, jewellery, glasses, body changes, facial-hair changes and other identity-changing details unless canon/appearance state explicitly authorises them.

## 3. Where references live

```text
studio/var/cast/
  <slug>/
    reference.json
    a-full-length.png
    b-head-shoulders.png
```

Stable slugs:

`gary`, `damo`, `sk`, `brock`, `tommy`, `lucas`, `oliver`, `sophie`, `casey`, `mitch`, `emma`, `charlotte`, `ethan`, `grace`.

These generated bytes live under `var/` and are gitignored. `reference.json` records identity, model/generation provenance and version history.

### `reference.json`

```json
{
  "slug": "gary",
  "age_at_reference": 43,
  "model": "",
  "continuity_method": "reference-image",
  "generated_at": "",
  "generated_in": "ChatGPT | Gemini | other",
  "prompt_sha256": "",
  "frames": {
    "a": "a-full-length.png",
    "b": "b-head-shoulders.png"
  },
  "supersedes": null,
  "notes": ""
}
```

A provider seed may be recorded if a provider genuinely exposes one and it is useful for provenance, but **seed reuse is never the continuity contract**. The file/version is.

A canonical reference is never silently overwritten. When identity is deliberately regenerated, preserve the superseded version because previously approved scenes may depend on it.

---

## 4. Reference generation

Use `CAST_REFERENCE_PROMPTS.md` only to create or deliberately replace reference assets. Once an approved file exists, the file outranks the old generation prose for scene continuity.

For a paired reference set:

1. Generate/approve frame A (full body).
2. Generate frame B using frame A as the identity reference in the same supported workflow/session where practical.
3. Compare B against A before approval.
4. Record the exact approved files in `reference.json`.

Do not assume a reusable random seed will preserve identity across providers.

Family resemblance is a deliberate visual requirement for Gary, Damo, Emma and Grace, but each remains a distinct person.

## 5. Using references in a scene

### 5.1 Production identity vs literal prompt wording

The production system **must** know the character by canonical slug/name. The literal provider-facing prompt does not need to use that name as a visual instruction.

Example production manifest:

```text
character: damo
identity reference: studio/var/cast/damo/a-full-length.png
face reference: studio/var/cast/damo/b-head-shoulders.png
scene appearance: W01-NIGHT-01
provider role: "the man from reference 1"
```

This preserves the world convention that generation prose can remain anonymous while eliminating the old ambiguity where `one bloke` could quietly become a different bloke.

### 5.2 Which frame to supply

| Need | Preferred reference |
|---|---|
| Full figure / build / body proportions | Frame A |
| Face-critical close or medium work | Frame B |
| Hero shot where both face and build matter | A + B when provider capacity and reference behaviour support it |
| Continuation after a successful in-world shot | Approved adjacent/in-world frame may supplement or outrank base pose for scene continuity, while canonical identity reference remains available |

Do not attach redundant references simply because they exist. Equally, do not impose an arbitrary hard cap such as "four characters" across every provider/model.

**Current rule:** use the minimum sufficient set that removes ambiguity without introducing conflicting visual inputs, within the current provider/model's documented limits and observed performance.

Provider capabilities change. Verify the current model before treating a reference-count limit as universal.

### 5.3 Reference-role declaration

Every attached image should have a declared role where ambiguity is possible:

- canonical identity
- full-body/build
- current wardrobe
- prop
- location
- first-frame anchor
- last-frame anchor
- adjacent approved shot

This role must also be persisted in the generation reference manifest per `AI_GENERATION_PIPELINE.md`.

## 6. What a canonical identity reference does and does not carry

### It carries

- face identity
- underlying body/build proportions
- stable hair/face characteristics visible in the approved file
- approved distinguishing physical characteristics

### It does not automatically carry

- the reference's base studio outfit into every world scene
- the reference pose
- studio lighting/background
- temporary expression
- temporary prop
- scene-specific dirt/wetness/damage

Scene wardrobe and mutable appearance come from resolved appearance state.

### It must not be contradicted casually

A scene may deliberately change mutable things such as a hat, layer, wetness or beard state **only when the scene/appearance contract says so**. Omission is not permission to invent a permanent characteristic.

## 7. Four common use cases

### 1. Scene from a story arc

The story arc names its cast internally. Resolve the slugs and scene appearance. Supply only the references that the provider needs for the shot, then write provider prose around moment/place/light/camera/action.

### 2. Shot specification

The shot contract carries canonical subjects and appearance state. The generation manifest resolves those subjects to exact files/version IDs.

### 3. Product in a world

Character reference supplies identity; approved garment/design reference supplies the product; scene appearance supplies how it is worn; the scene supplies everything else.

### 4. Continuity check

A later scene must be reviewable against the exact approved identity/reference version used. Identity drift should be provable from the persisted manifest rather than argued from memory.

---

## 8. Flow / provider-native reusable characters

Where a provider such as Flow offers a reusable Character or equivalent persistent identity object, it may be created **from the approved canonical reference assets** and used as an execution convenience.

It does not replace repo canon.

Record:

- provider
- provider character/object ID if available
- source canonical reference version
- creation date
- any voice reference linked to it
- known limitations

If the provider-native character drifts from the approved reference, the provider object is wrong; the repo canon does not change to match it.

## 11. Rejection rule

A generated asset fails character continuity if a meaningful recurring character:

- is the wrong person
- is only loosely similar to the approved identity
- acquires an unauthorised distinguishing feature
- loses an approved distinguishing feature
- has an unexplained build/age/hair/facial-hair shift
- wears the wrong resolved scene appearance
- is duplicated or missing contrary to the shot contract

Do not present a known-failed asset as an acceptable candidate simply because the scene/environment is otherwise good.
