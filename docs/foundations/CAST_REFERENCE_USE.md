# Cast references — storage and use

**Status:** Production asset. Companion to `CAST_REFERENCE_PROMPTS.md`, which
holds the fourteen prompts. This holds where the images live and how a scene
uses them.
**Date:** 15 August 2026.

---

## 1. What a reference is for

`CHARACTER_CONTINUITY.md` §10: *a recurring campaign character cannot exist only
as a prompt paragraph.* Before references, every scene prompt described five
people from scratch — which bloated the prompt, buried the moment, and produced
slightly different people each time.

After references, a scene prompt is **the moment, the place, the light and the
camera**, and the people arrive as images.

That only holds if the reference is stable. A reference regenerated is a
different person, so **the file is the asset** — not the prompt, and not a seed.
The generators in use expose no reusable seed; continuity is held by supplying
the reference image itself to every subsequent generation of that character.

## 2. Where they live

```
studio/var/cast/
  <slug>/
    reference.json          identity, model, prompt hash, date, provenance
    a-full-length.png       frame A
    b-head-shoulders.png    frame B
```

`slug` is lowercase and stable: `gary`, `damo`, `sk`, `brock`, `tommy`, `lucas`,
`oliver`, `sophie`, `casey`, `mitch`, `emma`, `charlotte`, `ethan`, `grace`.

**Under `var/`, so gitignored.** Same convention as `design_corpus` and
`design_archive` — generated bytes stay out of the repository, and
`reference.json` records enough to regenerate or to prove which image was used.

### `reference.json`

```json
{
  "slug": "gary",
  "age_at_reference": 43,
  "model": "",
  "continuity_method": "reference-image",
  "generated_at": "",
  "generated_in": "ChatGPT | Gemini | Claude",
  "prompt_sha256": "",
  "frames": { "a": "a-full-length.png", "b": "b-head-shoulders.png" },
  "supersedes": null,
  "notes": ""
}
```

`prompt_sha256` is the hash of the prompt actually used, so a change to
`CAST_REFERENCE_PROMPTS.md` can be detected against every existing reference
rather than silently diverging from it.

There is no seed field. An earlier draft had one and told people to record it;
the generators in use return `seed: null`, so it was a field that could never be
filled and advice that could never be followed.

`supersedes` points at a previous reference directory when a character is
regenerated. **A reference is never overwritten** — a new one is written beside
it and the old one kept, because scenes already shot against the old face are
still canon.

## 3. Generating them

Per the standing decision, no metered API. The prompts are taken to a paid
ChatGPT, Gemini or Claude interface and the files brought back.

Order matters once: **Gary first.** Emma, Grace and Damo are matched to his brow
and eye set, so his reference is the anchor. Generate his frame A, then generate
frame B **in the same conversation with frame A attached** — that is what holds
the face, since no seed is available. The other three family faces are generated
the same way, with Gary's frame A supplied as a resemblance reference.

Everyone else is independent and can be generated in any order.

## 4. Using them in a scene

### The shape of a scene prompt after references

Before:

> Five people outside a servo at 2am. A man in his forties with deep-set eyes and
> a heavy brow wearing a dark jumper, a younger man with untidy hair in an olive
> t-shirt, a woman with dark hair up in a black vest… *(and so on, for 200 words,
> before the scene has been described at all)*

After:

> Outside a servo at 2am. Sodium light, wet asphalt, the shop window the only
> other source. Four of them on the kerb, one still at the pump. Shot from across
> the forecourt at 35mm, waist height. **[reference: gary, damo, emma, brock]**

The people are supplied as images. The prompt is the moment.

### Which frame to supply

| Scene need | Frame |
|---|---|
| Full figure, any distance | A |
| Close work, faces carrying it | B |
| Both in one scene | A and B for that character |

Never supply more than four characters' references to one generation. Beyond
that the model averages them and the resemblance collapses — supply the ones the
frame is actually about and let the rest be "another mate" in the prose.

### Four use cases, in the order they will come up

**1. Scene from a story arc.** `STORY_ARC.md` scenes name their cast. Pull those
slugs, supply frame A for each, write the scene as place, light, moment, camera.
This is the common case.

**2. Shot spec.** `shots/W01-P22.md` is the worked example — a full SHOT_SPEC
already carries its cast list. The references make the *Subjects* section a list
of slugs instead of four paragraphs of description.

**3. Product in a world.** The product pipeline hands over a finished design;
the world pipeline puts it on a person in a place. Reference supplies the person,
the approved design supplies the garment, the scene supplies everything else.
This is the seam between the two pipelines and the only place they touch.

**4. Continuity check.** Two scenes months apart should hold the same face.
`reference.json` records which reference was used, so a drift is provable rather
than argued about.

### What a reference never does

- **Never carries wardrobe into a scene.** Base wardrobe exists so the reference
  reads as a person, not an outfit. Scene wardrobe is stated per scene, always.
- **Never carries a name into a prompt.** `WORLD.md`'s Form rule stands: "one
  bloke", "a woman", "another mate". The slug is a file path, not prompt text.
- **Never ages.** `age_at_reference` is recorded because a world set five years
  on needs a new reference, not a note that the face is wrong.

## 5. What was decided while it ran

**All fourteen exist.** Both frames each, generated 15 August 2026 in the
owner's subscription UI. Nothing here is pending any more.

The section this replaces warned that a generator would quietly assign the
cast a look nobody chose. That is roughly what happened, and it was corrected
in flight rather than in advance — four decisions came from the owner while
looking at output, which is faster than deciding fourteen characters' worth of
appearance from a blank page:

| Decision | Why |
|---|---|
| Charlotte is blonde | She was the third dark-haired woman of about the same age with a similar blunt cut, after Emma and Casey |
| Grace is strawberry blonde, from her mother | She and Emma are half-sisters; the maternal line explains why they differ while both carry Gary's brow |
| Casey wears white, not black | Black head to toe was SK's silhouette exactly |
| Mitch wears black Docs, not clogs | Clogs are work footwear and the reference is not at work |

Ethnicity and skin tone were never stated and were left to the generator. It
produced a uniformly white cast. That is now what the references are, and
changing it means regenerating, not editing a document.

Two family faces were matched against Gary's frame A — Emma and Grace — and
Damo was regenerated against it after his background landed. Ethan was
deliberately not: he is Grace's boyfriend, not blood, and attaching Gary would
have made him look like her brother.
